# План реализации URL shortener в React

## Цель
Собрать приложение в папке [D:/TopIT/link_shortener/JS+React/link shortner](D:/TopIT/link_shortener/JS+React/link shortner), которое:
- создает короткий URL из длинного;
- возвращает длинный URL по короткому;
- считает количество переходов (резолвов короткой ссылки);
- ограничивает количество хранимых URL значением, заданным при старте;
- при переполнении удаляет запись с минимальным `hitCount`, а при равенстве — самую раннюю по `createdAt`;
- реализовано в ООП-стиле и максимально оптимизировано по операциям поиска/обновления.

## ООП-архитектура
- `class UrlEntry`
  - инкапсулирует данные одной ссылки: `id`, `longUrl`, `shortCode`, `hitCount`, `createdAt`.
  - методы: `incrementHits()`, `toJSON()`, `static fromJSON(raw)`.
- `class UrlRepository`
  - отвечает только за загрузку/сохранение коллекции в `localStorage`.
  - методы: `load()`, `save(entries, capacity)`.
- `class UrlShortenerService`
  - основной доменный сервис с инкапсуляцией алгоритмов.
  - хранит индексы (`Map`) и предоставляет API: `init(capacity)`, `shorten(longUrl)`, `resolve(shortCode)`, `list()`.
  - внутри реализует политику вытеснения LFU+FIFO.
- `App.jsx` использует только публичные методы `UrlShortenerService`, без прямой работы с `localStorage` и без бизнес-логики внутри компонентов.

## Оптимизация (обязательные критерии)
- Индексы `Map`:
  - `longToShort: Map<longUrl, shortCode>` для быстрого `reuse` (O(1) в среднем).
  - `shortToEntry: Map<shortCode, UrlEntry>` для резолва и инкремента счетчика (O(1) в среднем).
- Операции `shorten/resolve` должны выполняться без полного сканирования коллекции в обычных сценариях.
- Персист в `localStorage` выполнять батчево после изменения состояния (один `save` на одну доменную операцию).
- Генерация `shortCode` — короткий base62 код с проверкой коллизий через `Map`.
- Вытеснение при переполнении:
  - вычислять кандидата по `min(hitCount)` и затем `min(createdAt)`;
  - после удаления синхронно обновлять оба индекса.

## Проектирование данных
- Формат записи:
  - `id: string`
  - `longUrl: string`
  - `shortCode: string`
  - `hitCount: number`
  - `createdAt: number` (unix ms)
- Хранилище в памяти: коллекция записей + два индекса `Map` + `capacity`.
- Ключ `localStorage`: фиксированный, например `link_shortener_store_v1`.

## Логика и алгоритмы
- **Инициализация при старте**
  - экран первичной настройки: пользователь вводит `capacity` (целое > 0);
  - после подтверждения значение фиксируется и сохраняется в `localStorage`.
- **Создание короткой ссылки**
  - валидация URL через `new URL(...)`;
  - если `longUrl` уже существует — вернуть существующий `shortCode`;
  - иначе сгенерировать уникальный `shortCode`;
  - если достигнут лимит, выполнить вытеснение `min(hitCount)` + `oldest(createdAt)`;
  - добавить новую запись с `hitCount = 0`.
- **Резолв короткой ссылки**
  - поиск по `shortCode`;
  - если найдено: вернуть `longUrl`, увеличить `hitCount`, сохранить изменения;
  - если не найдено: показать ошибку "короткая ссылка не найдена".
- **Подсчет переходов**
  - счетчик увеличивается только при успешном резолве короткой ссылки.

## Риски и контроль
- Риск: коллизии `shortCode`.
  - Контроль: генерация в цикле с проверкой уникальности через индекс `Map`.
- Риск: неконсистентные данные в `localStorage` (ручная порча).
  - Контроль: безопасный `JSON.parse` + fallback на пустое состояние.
- Риск: деградация производительности на больших capacity.
  - Контроль: все горячие lookup-операции через `Map`, без линейного поиска.
- Риск: пограничные кейсы capacity.
  - Контроль: строгая валидация числа (>0).
